# ADR 0031: share allocation route authority reads

Date: 9 September 2026. Status: implemented; 17 command-journal checks passed. Complete repository verification and deployed qualification remain pending.

The allocation inbox acquires its finite route set in stable order before taking the outbox admission budget. That ordering prevents the demonstrated mixed-zone deadlock described in [ADR 0021](0021-bounded-inbox-transactions.md). It used exclusive route locks even though allocation registration only reads route owner, epoch and state. An uncommitted allocation batch therefore blocked command authority reads in every zone, including commands for already committed, independent allocations. [ADR 0029](0029-share-command-route-authority-reads.md) had removed contention between command readers, but left this allocation-reader conflict in place.

Both the ordered inbox route acquisition and the individual allocation registration now use `FOR SHARE`. Registration must not upgrade the shared batch lock to exclusive. The entire finite route set is still acquired before the shared outbox budget, and the locks last through inbox commit. Command readers can proceed together; updates to owner, epoch or state still conflict, including updates that preserve route keys. [PostgreSQL row-lock modes](https://www.postgresql.org/docs/18/explicit-locking.html#LOCKING-ROWS).

Movement identity remains protected by its transaction advisory lock and database uniqueness. Assignment rows, events and inbox ownership still commit atomically. Pending release, baseline registration, cancellation, migration and restoration retain their existing locks. No route writer, command identity, equipment proof, worker count, retry rule or durability setting changes. Shared tuple locking still has a cost and does not remove the outbox budget's required serialization.

`allocationInboxSharesAuthorityWithCommandsButStillFencesOwnerChanges` holds an actual applied inbox transaction open. Two commands for previously committed allocations, in the same and another zone, must commit before that batch is released. PostgreSQL blocker identities distinguish actual contention from a scheduling timeout. A concurrent owner/epoch update must remain blocked by the batch until commit; afterward, dispatch of its old-owner allocation must fail. The test also verifies that the held allocation remains invisible to another transaction before commit and that no physical effects are invented.

The new regression failed against the previous implementation at **06:13:16 Europe/Berlin** on the assertion that an allocation inbox must not block command authority readers. All **17 command-journal checks** passed after the correction at **06:14:36**, with zero failures, errors or skips, including the existing mixed-zone route/budget deadlock regression. These component results establish concurrency and fencing behavior, not an A50 latency pass. Full sustained qualification still requires the unchanged workload and complete [post-commit timing proof](0030-prove-dispatch-timing-after-commit.md).
