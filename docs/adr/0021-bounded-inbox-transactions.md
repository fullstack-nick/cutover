# ADR 0021: bounded inbox ownership transfers

Date: 8 September 2026. Status: implemented; component, deployed process-crash and queue-overflow regressions passed; sustained-load qualification pending.

The full `968cad5` load run completed all 3,300 physical/business effects once, but only 85.9% of the 3,000 measured movements reached durable adapter acceptance within two seconds of original eligibility (p99 8,340.798 ms). Individual task-created latency was much lower and does not replace that denominator. Slow intervals included publication confirmation and consumption waits; one retained trace overlaps a database checkpoint. Checkpoint overlap is evidence of shared storage contention, not proof that every delayed delivery has the same cause.

The pull consumer previously committed each delivery separately. It now reads at most 16 deliveries per runtime iteration (the API rejects batches above 32), transfers their durable inbox/quarantine ownership in one PostgreSQL transaction, and acknowledges individual delivery tags only after that transaction returns successfully. It does not wait for a batch to fill. A 64-KiB message bound limits a runtime batch to at most 1 MiB of message bodies, plus bounded decoding overhead. Basic-get does not use prefetch as its bound. Acknowledgements must use the receiving channel, and unacknowledged deliveries are requeued when that channel closes. [RabbitMQ acknowledgement documentation](https://www.rabbitmq.com/docs/confirms)

Each business handler retains its nested savepoint. A poison handler can leave its own message pending/quarantined while healthy peers commit; an admission or connection failure outside that handler rolls back the entire transfer. No member of a failed transfer is acknowledged. The runtime transport backoff applies before replay. This intentionally allows a blocked storage admission to delay the bounded group; it never permits partial acknowledgements of uncommitted peers. jOOQ's transaction-scoped configuration is passed to every nested operation. [jOOQ transaction documentation](https://www.jooq.org/doc/latest/manual/sql-execution/transaction-management/)

A process crash after the batch commits can repeat several deliveries, including peers whose individual acknowledgements had not reached the broker. Original event IDs, stream constraints, typed raw-quarantine ownership and business uniqueness still suppress repeated effects. Database `fsync` and synchronous commit remain enabled. Consumer transaction grouping changes no event contract, schema, route epoch or physical command identity.

Required checks cover a real quorum batch crash before its first acknowledgement, complete rollback when a later member exceeds retained storage, separate handler savepoints/raw quarantine, existing single-message and publisher-failure checks, and renewed runtime crash/overflow/load qualification. No performance improvement is claimed before measurement.

The first full load with batching, `load-1788893862792` on `c6486a6`, exposed an adapter lock-order regression. All 3,300 effects eventually completed once, but only 6.1% of the 3,000 measured movements met two seconds (original-eligibility p99 156,213.575 ms). The retained PostgreSQL log contains 305 deadlock errors: a mixed-zone inbox transaction held the shared outbox admission row while waiting for a later route, and another writer held that route while waiting for admission. This is direct lock-cycle evidence; it replaces storage-contention speculation for this regression.

Before registering the first movement in an inbox transaction, the adapter now locks its finite route set in `(site_id, zone_id)` order. Those locks precede the shared outbox budget and remain held through the bounded batch. Locking only the current site would leave the same inversion possible across sites, because the admission row belongs to the whole adapter database. Observation-only handlers do not acquire route locks. Existing command and migration writers retain their route-before-budget order. This deliberately serializes short allocation transactions across the six seeded routes; it adds no network call inside those locks and does not change route ownership, epochs, message identities or WAL durability.

`mixedZoneInboxBatchDoesNotInvertRouteAndOutboxBudgetLocks` reproduces the cycle using two actual PostgreSQL transactions and verifies the competing backend through `pg_blocking_pids`. The old code leaves one inbox effect pending; the corrected code commits both inbox effects plus the competing allocation. The focused test failed before the fix and passed after it. The full adapter reactor then passed all 56 checks with no failures, errors or skips. Renewed deployed load remains a separate gate.
