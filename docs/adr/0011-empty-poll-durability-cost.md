# ADR 0011 — keep empty polling read-only

Status: accepted, 8 September 2026. Component verification and the idle runtime comparison passed.

Migration observations exposed occasional dispatches above two seconds despite single physical effects. Replacing the broker's frequent Erlang CLI readiness check removed substantial CPU throttling, but another latency miss remained. Application database statistics then showed 2,593 client-backend WAL fsyncs over five idle snapshots spaced five seconds apart, with 8,558.992 ms of cumulative fsync wait. No business traffic was submitted during that interval.

The relay, inbox retry loop and task/equipment workers acquired control or quota row locks even when their work queues were empty. A PostgreSQL row lock can itself [cause a disk write](https://www.postgresql.org/docs/18/explicit-locking.html). These transactions were needlessly competing with accepted work for durable storage.

Each affected poll now checks for eligible work using an ordinary read before entering its existing write transaction. A false result only defers a concurrent new arrival until the next bounded poll. A true result grants no authority: the transaction still checks the freeze/admission controls, locks the selected rows, rechecks their eligibility and records durable leases. An item claimed by another process cannot be processed by virtue of the earlier read.

The outbox keeps per-stream ordering and publisher confirmations; the inbox keeps storage admission and transactional effects; the adapter keeps its route and journal gates. `fsync` and synchronous commit remain enabled. Failed migration latency samples are immutable, so they also cease repeated background proof reads and remain available for an explicit supervisor reversal.

Meaningful regression checks run empty delivery/equipment polls in actual PostgreSQL read-only transactions, verify that no write transaction ID is assigned, then prove a later event still publishes and applies once. The full 105-check verification also retains crash, duplicate, freeze and state-transition checks. `tools/scenario-driver/wal-idle-smoke.mjs` records live WAL counts and timings without resetting counters or changing durability. Its short diagnostic is separate from the final ten-minute mixed-product load test.

After the existing environment received the verified images, run `wal-idle-1788834542817` measured **21 fsyncs in 20.809 seconds**, about **1.009 per second**, and **66.143 ms** cumulative fsync wait. This is approximately a 99% reduction in idle flush frequency. The rollout preserved application volumes and the simulator's world, journal generation and physical high-water mark of 149. The first simulator post-restart read encountered a closed connection; a fresh connection and comparison with the prior retained physical proofs verified its unchanged history.

The first traffic check after the simulator image update exposed an omitted migration: that independent database still had V104, while the current shared durability guard required V107. The simulator rejected admission before any physical acceptance, and the adapter retained an unknown command after its bounded retries. `scripts/update-simulator.ps1` now stops only the named simulator process, applies its migrations and starts it with the same volume. After the actual V104→V107 upgrade, a supervisor investigated the original command; matching-world absence allowed the same ID to execute, and the physical/inventory ledgers each contain one effect. The deployment failure remains recorded rather than being hidden by the earlier passing idle measurement.
