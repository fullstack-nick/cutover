# ADR 0030: prove dispatch timing after commit

Date: 9 September 2026. Status: implemented in the workload verifier; four focused checks and a complete retrospective runtime replay passed. Full sustained qualification remains open.

The workload's original endpoint was `command_journal.created_at`. The journal writes this value inside its transaction, before the commit returns. This endpoint includes assignment, delivery and scheduling delay but can understate durable acceptance latency during slow commits. A full run already failing on this earlier endpoint remains failed. A passing earlier endpoint would be insufficient to qualify the intended durable-acceptance target.

The actual HTTP adapter controller directly calls `CommandJournal.record`, without an enclosing controller transaction. Its `cutover.command.record` domain span wraps `recordTraced`; the supplier returns after the jOOQ transaction has committed, and `OperationTrace.call` then closes the span. The verifier can therefore use that successful span's end as an observed upper bound on transaction completion. This is a verification dependency only: traces still grant no runtime authority and drive no business state change.

After the offered workload and resource sampling end, the verifier reads original assignment trace contexts from the adapter's retained outbox. Every movement needs its own successful adapter journal span, matched by original movement identity within the original trace. Shared order traces cannot substitute a neighboring movement's timing. Error spans, absent coverage or a span ending before its journal row are rejected. The verifier fetches each distinct trace once and retains a bounded maximum of 5,000 movement rows. HTTP reads have a ten-second timeout.

Original eligibility remains the start. Span end rounds up and eligibility rounds down to milliseconds so submillisecond truncation cannot create a pass. The existing primary dispatch metrics now use this post-transaction bound; the earlier journal-timestamp metrics remain named diagnostics. All movements remain included, the workload remains unchanged, and the target remains at least 99% within two seconds. Missing timing proof fails qualification. `durable-dispatch-timing.json` records each matched span and timing.

The complete retrospective audit of `load-diagnostic-1788925571030` covered **650 movements**, including **600 measured movements**, through **390 original traces**. Its original row-timestamp result was **93.0% / 7,101.515 ms p99**. The post-transaction bound was **92.833% / 7,189 ms p99**. The journal-timestamp-to-return gap reached **475 ms**, with **207 ms p99**. These are measurements of the same completed work, without reoffering requests or changing the original result. The run fails under both endpoints.

`node --test tools/scenario-driver/durable-dispatch-timing.test.mjs` passed four checks: a late commit cannot pass because of an earlier row timestamp; shared trace identities and failed spans cannot substitute coverage; missing/duplicate contexts fail; and rounding remains conservative at the two-second deadline. The actual runtime replay using the same exported verifier exactly reproduced all 650 observations. Original focused-test log SHA-256: `f68f9afe642d4e82a89e5ce785479cfe9566449df713627276fa5776b905f31e`. Replay artifact SHA-256: `bc0fa5bd1b0af2e9b91763a9ed7d0a7dcd4edfcc85763c415b214234cdaabd03`.

The Java applications remain the packages verified by the complete 203-check run. A new source-level verifier does not turn the two-minute diagnostic into the required ten-minute A50 qualification. Future application refactoring must preserve the documented span/transaction boundary or replace this proof method before claiming a pass.
