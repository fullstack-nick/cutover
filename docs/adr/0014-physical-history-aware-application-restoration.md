# ADR 0014: Reconcile application restores against independent physical history

Status: accepted; running-platform verification is tracked separately in the implementation ledger.

An application checkpoint can be internally consistent yet older than the equipment's physical work. Replaying its messages is insufficient to establish safe dispatch. The simulator's completion ledger also omits accepted commands that have not executed. Both records must be considered.

Restore into the separately named `cutover-restored` kind cluster, with separate PostgreSQL and broker volumes and an explicit kubeconfig. Verify checkpoint and cached image checksums before stopping the original Cutover node. Import only into empty owner databases, in per-database transactions, and compare every table fingerprint before starting writers or adding recovery bookkeeping. Recreate broker topology from its saved definitions and replay the qualified retained outbox range with original event IDs and bytes. Each owning service uses its own restricted database and broker credentials. Retention is temporarily held in this recovery profile.

Adapter V117 adds a durable `restoration_required` gate and bounded owner-local recovery evidence. This gate blocks new allocation, dispatch and route changes even if ordinary diagnostic control flags are reopened. Existing command status investigation and completion delivery remain possible. Recovery never sends equipment commands, creates missing business intent, invents inventory effects or restores the simulator database.

The adapter compares all retained physical completion rows and the simulator's paged command inventory with its original allocations and command payloads. Every restored command absent from that inventory needs an individual, fresh, same-world 404 proof and must never have been accepted. Transport errors cannot establish absence. World or journal-generation changes, incomplete/rewound history, changing command-inventory counts and missing/conflicting intent keep dispatch held. Missing business context is recorded as an RPO gap, not a recovered order.

Verification binds route ownership, command/allocation intent and physical/inventory/absence proofs. Release rechecks the current world and inventory frontier, requires the expected session version and records actor, reason and before/after versions. A known completion arriving between verification and release expires verification, so the same session can extend its proof. Unknown work or conflicting evidence is quarantined. Ordinary intake/dispatch controls remain closed until the explicit local lifecycle procedure has completed release and replay verification.

Evidence is bounded to 20,000 physical rows, 20,000 simulator command records and 32 MiB of retained proof per session, with at most 16 retained sessions. Completion pages hold at most 100 rows, command pages at most 32, absence batches at most 16 and replay batches at most 32 events. Capacity exhaustion fails closed. These are procedural bounds, not measured throughput claims.

Only one Cutover application environment may be active against the simulator. Resuming the original demo after a restore experiment requires unchanged simulator world/generation and command count since that primary was stopped. A freeze and identity hash of accepted orders and receipts also prevents abandoning newly accepted work that has not sent a command yet. If the restored environment accepted additional work, retain its application storage. Stop records its control flags and preserves storage; Start requires the primary to remain stopped and restores those flags through versioned requests after fresh processes become ready. Removing the separately restored cluster is a distinct, explicitly named action. No lifecycle operation targets unrelated projects.

The first supported checkpoint images include V117 and its recovery commands. Earlier checkpoint artifacts remain checksum-verifiable, but their application images lack this procedure; using them requires a separately tested compatibility path. The current procedure is not host-loss protection, continuous backup or a zero-RPO guarantee. The quiescent restore target is 15 minutes; its actual duration and stale-checkpoint behavior require deployed evidence.
